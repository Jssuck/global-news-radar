# 开发进度严格把控机制

> **目的**：把里程碑交付从「期望」变为「可度量、可预警、可裁决」的过程，防止开源项目最典型的进度失控——无度量的拖延与无决策的范围蔓延。
> **适用范围**：核心团队迭代开发、里程碑 Gate Review、社区贡献者任务管理；排期基准为设计文档 v1.0 第 7 章（15 周基准，12–16 周弹性）。
> **关联文档**：里程碑出口标准见 `03-acceptance-criteria.md`；阶段流转规则见 `01-lifecycle.md`；KPI 自动化采集见 `05-harness-enforcement.md`。

## 1. 节奏：双周迭代 + 里程碑门禁评审

### 1.1 双周迭代

以双周（对齐设计文档 14 天粒度的甘特计划）为固定节奏，每期三个固定会议：

| 会议 | 时点 | 时长 | 内容 | 产出 |
|---|---|---|---|---|
| 迭代计划会 | 第 1 天 | ≤90 min | 从里程碑 backlog 拉取本期任务；确认里程碑入口条件；任务指派到人 | 迭代看板（GitHub Projects） |
| 期中站会（异步优先） | 第 6–8 天 | ≤30 min | 阻塞项暴露；黄灯预警初判 | 阻塞清单与升级记录 |
| 迭代评审+回顾 | 最后 1 天 | ≤90 min | 按 DoD 演示完成项；KPI 快照；回顾一条改进项 | 迭代报告（含 KPI 表快照） |

规则：任务粒度 ≤3 天，超过须拆分；每期迭代预留 ≥20% 容量给 review、告警处置与源修复派单，禁止排满；跨里程碑的并行（M3 与 M2）以契约冻结为唯一同步点，不按迭代强行对齐。

### 1.2 里程碑门禁评审（Gate Review）

每个里程碑出口召开一次 Gate Review，是项目唯一的「过/不过」裁决场合：

- **参与人**：全体 Maintainer、Release Manager（主持）；Committer 可列席无表决权。
- **输入**：`scripts/gate_check.py` 的 PASS/FAIL 报告（见 `05` 文档）、人工抽检记录、签字记录模板（见 `03` 文档附录）。
- **裁决规则**：`03-acceptance-criteria.md` 中该里程碑全部「必须通过项」PASS → 通过；任一 FAIL → 不通过，进入第 3 节延期处置。禁止以口头承诺替代指标。
- **输出**：签字记录归档至 `docs/gate-reviews/Mx-signoff.md`，并在 CHANGELOG 记录里程碑达成。

## 2. 进度度量 KPI

以下 KPI 为强制度量项，数据源与采集自动化约定见 `05` 文档；验收类 KPI 的门槛值与 `03-acceptance-criteria.md`、设计文档第 7 章完全一致。

| KPI | 定义 | 数据源 | 频率 | 健康阈值 | 责任角色 |
|---|---|---|---|---|---|
| 里程碑燃尽 | 当前里程碑剩余任务点 / 剩余工作日 | GitHub Projects | 每周 | 燃尽线在理想线 ±15% 内 | Release Manager |
| 源覆盖率 | 已入库且近 24h 成功抓取的源数 / 目标数（M1:300，M4:1,000，150+ 国家） | 源注册表+健康统计 | 每日 | 按里程碑目标；国家数 ≥150（M4） | Maintainer |
| 抓取成功率 | 全库滚动 24h 抓取成功任务占比 | 健康度看板 | 每日 | ≥90%；单源连续 0 触发断更告警 | Maintainer |
| 正文抽取成功率 | 一级清洗产出合格正文占比（对照人工标注基线） | 管线指标 | 每周 | ≥90%（200 篇标注样本基线） | 数据/LLM 工程师 |
| 质量门 1 判负率 | 送第二级 LLM 清洗流量占比 | 管线指标 | 每日 | ≤20%；10–20% 为告警带 | 数据/LLM 工程师 |
| LLM 月成本 | 全管线 LLM 账单（冷启动全 API） | 成本监控 | 每周 | ≤$100/月 | 数据/LLM 工程师 |
| 渲染流量占比 | Playwright 渲染抓取 / 总抓取 | 管线指标 | 每周 | ≤15% | 后端工程师 |
| CI 通过率 | main 分支近 30 天 CI 成功率 | GitHub Actions | 每周 | ≥95%；连续 2 次红即冻结合并 | Maintainer |
| issue 积压 | 未响应 issue 数（超 72h 无首次响应） | GitHub | 每周 | 0（Incubating/Active 阶段） | Maintainer 轮值 |
| PR 周转时间 | PR 从开启到首个评审意见 | GitHub | 每周 | 中位数 ≤72h | Maintainer 轮值 |

## 3. 延期处置：黄灯/红灯升级与范围裁剪

### 3.1 升级机制

| 级别 | 触发条件（任一） | 处置动作 | 决策人 |
|---|---|---|---|
| 绿灯 | KPI 均在健康阈值内 | 正常推进 | — |
| 黄灯 | 里程碑燃尽偏离 >15%；或任一验收类 KPI 连续 2 周低于阈值；或关键路径任务延期 >3 天 | 期中站会正式记录；责任工程师提交追赶计划；下一迭代削减 20% 新任务量 | Release Manager |
| 红灯 | 黄灯处置后 1 个迭代内未恢复；或预计里程碑出口延期 >1 周；或验收类 KPI 出现结构性不达标（如判负率击穿 20% 红线且调优无效） | 48h 内召开 Maintainer 专项会，执行范围裁剪决策树；结果写入迭代报告 | 全体 Maintainer 表决 |

### 3.2 范围裁剪决策树

红灯触发时按固定优先级裁剪，**砍特性不砍质量**（设计文档 7.3.1 的硬约束）：

1. **第一刀：可顺延特性**——WebSub 推送、每日离线 HDBSCAN 校正、多架构镜像以外的发布工程 → 顺延 v1.1。
2. **第二刀：非关键路径范围**——源清单国家数下限从 150+ 降至 120+（须公告）、第三级整理的翻译语种范围缩减。
3. **第三刀：周期置换**——以延迟换折扣：第二级 LLM 清洗全量改走 Batch API 离线回填（约 50% 折扣），第三级整理降级为「未整理占位」不阻塞入库。
4. **禁止裁剪**：三个质量门、地域受限检测-提示机制、robots.txt 遵守与礼貌限速、许可证扫描门禁——这四类是正确性/合规/成本底线，任何情况下不可顺延或降标。
5. **最后手段**：上述仍无法恢复时，里程碑周期顺延（上限：总周期 16 周），并在 GitHub Discussion 公告社区。

## 4. 社区贡献者任务认领与停滞回收

源适配器与源清单策展自 M1 起对社区开放（RSSHub 路由贡献模式），其进度风险以认领制管控：

| 规则 | 内容 |
|---|---|
| 认领 | 在「请求新源」或 `good first issue` 类 issue 下评论认领，由 Maintainer/Committer assign；同一 issue 同时只 assign 1 人；每人同时认领 ≤3 个 |
| 停滞判定 | **issue assigned 后 14 天无任何活动**（无 commit、无 PR、无评论更新）即判定停滞，由机器人（如 stale bot / GitHub Actions 定时任务）自动评论提醒 |
| 回收 | 提醒后 72h 仍无响应 → 自动 unassign，issue 回到待认领池并打 `recovered` 标签；认领人此前的半成品分支保留供接手者参考 |
| 宽限 | 认领人评论说明合理原因（如目标站反爬排查中）可申请一次 14 天宽限；宽限不续期 |
| 源维护者责任 | 源适配器合入后，认领人自动成为该源的源维护者；健康度看板断更告警即派单输入，连续失效且 30 天无人修复的源进入弃用清单 |
| 防占坑 | 同一贡献者累计 3 次被回收后，认领须 Maintainer 手动批准 |

设计意图：数据源型项目的进度黑洞不在代码而在「源腐化与任务占坑」，14 天自动释放保证待办池始终流动；派单-回收闭环使源维护从核心团队负担转化为社区分工（设计文档 7.3.1 社区共建节奏的落地机制）。

## 5. 记录与审计

迭代报告、黄/红灯记录、Gate Review 签字记录均为仓库文档（`docs/gate-reviews/`），随代码同仓评审合入——进度数据的可见性本身就是约束：任何人可以随时核对 KPI 快照与里程碑承诺的差距。
